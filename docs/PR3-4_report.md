## 1. Мета й постановка

Побудувати демонстраційний криптографічний застосунок із підтримкою автентифікованого симетричного шифрування, RSA-OAEP, RSA-PSS, гібридного шифрування, управління ключами, тестування й оцінки продуктивності. Вихідний шаблон було проаналізовано та перероблено з урахуванням цілісності й конфіденційності.

## 2. Завдання №1. AES і захищене зберігання ключів

Генератор `secrets.token_bytes` створює майстер-ключ AES-128, AES-192 або AES-256. Система зберігає лише зашифровані версії ключів в `.crypto-lab/keys/`; пароль вводиться без відображення або отримується із середовища `CRYPTO_PASSWORD`. Захисний ключ виводиться з пароля за допомогою Scrypt із випадковим salt 16 байт, параметрами n=32768, r=8, p=1. Для захисту самого майстер-ключа використано AES-GCM із 12-байтним nonce, а метадані ключа автентифікуються як AAD.

При шифруванні даних створюється новий salt (16 байт), з майстер-ключа через HKDF-SHA256 виводяться ключі конкретного файла. У GCM використано випадковий 12-байтний nonce, а цілісність забезпечується GCM tag. У CBC застосовано випадковий IV 16 байт, PKCS#7 та HMAC-SHA256 у порядку Encrypt-then-MAC. HMAC перевіряється **до** CBC-дешифрування. Заголовок CSYM підписується/автентифікується.

Команда `sym rotate` генерує нову версію AES-ключа; попередня залишається в зашифрованому keystore для читання старих файлів. Ключі та паролі не виводяться в лог і не зберігаються відкритим текстом.

## 3. Завдання №2. RSA та цифровий підпис

Реалізовано генерацію RSA 2048/3072/4096 біт, `e=65537`. Приватний ключ експортується у захищений PKCS#8 PEM, публічний — SubjectPublicKeyInfo PEM. Шифрування короткого повідомлення виконується RSA-OAEP-SHA256; розшифрування — приватним ключем. Підпис — RSA-PSS із SHA-256, перевірка — за допомогою відкритого ключа. Передбачено виявлення зміненого вмісту й недійсного підпису.

Для RSA-OAEP з ключем 2048 біт і SHA-256 максимальна довжина повідомлення — `256 - 2×32 - 2 = 190` байт. Для великих файлів використовується гібридне шифрування.

## 4. Завдання №3. Гібридне шифрування

У модулі `crypto_lab/hybrid.py` кожен файл отримує окремий випадковий AES-256 ключ. Дані шифруються AES-GCM, AES-ключ загортається публічним RSA-ключем отримувача через OAEP-SHA256. Контейнер CHYB містить версію формату, nonce, відбиток відкритого ключа, довжину загорнутого ключа, RSA-частину та ciphertext із тегом. Заголовок і RSA-частина є AAD для AES-GCM.

Під час декодування приватний RSA-ключ відновлює AES-ключ, після чого AES-GCM перевіряє тег. Пошкодження файлу або використання чужого приватного ключа викликає помилку. Розшифрований файл не створюється.

## 5. Завдання №4. Продуктивність та відмовостійкість

**Фактичні вимірювання** зроблено 25.11.2026 в контейнері Linux/Python 3.13.5 (це **не Kali Linux**). Час визначено через `time.perf_counter_ns()`, по 5 повторів кожної операції; вказано медіану. Повні результати — `benchmarks/results.csv`, `benchmarks/results.json`, `benchmarks/results.md`. У таблиці вибірка значущих значень:

| Параметр | Шифрування (мс) | Дешифрування (мс) |
|---|---:|---:|
| AES-256-GCM, 1 MiB | 0.5099 | 0.2894 |
| AES-256-CBC+HMAC, 1 MiB | 2.5494 | 1.7382 |
| RSA-2048, 32 байти | 0.0284 | 0.3887 |
| RSA-3072, 32 байти | 0.0631 | 1.3093 |
| RSA-4096, 32 байти | 0.0925 | 3.7181 |

Для довгих файлів AES-256-GCM виявився швидшим у цій реалізації. RSA використовується для коротких даних/ключів; продуктивність приватних операцій падає зі збільшенням RSA-ключа. Детальну таблицю з key generation, sign, verify та іншими розмірами наведено в `docs/bench-analysis.md`.

Перевірено такі виняткові ситуації: неправильний пароль AES, неправильний пароль RSA, некоректний PEM, змінений байт GCM/HMAC, підроблений заголовок, зміна вмісту після підпису, невірний отримувач гібридного контейнера, надто великий вхідний блок RSA, недопустимі розміри ключів. Результат — контрольована відмова без створення неперевіреного plaintext-файлу.

## 6. Завдання №5. Інтеграція та журналювання

Консольна програма `cli.py` включає команди `sym new/rotate/list/enc/dec`, `rsa gen/enc/dec/sign/verify`, `hybrid enc/dec`, `bench`. Для шифрування доступні `--in` (файл) та `--text` (рядок UTF-8). Після операції CLI відображає алгоритм, розмір ключа, обсяг оброблених даних і час виконання. Журнал `.crypto-lab/logs/operations.jsonl` зберігає дату, тип дії, назву алгоритму, обсяг, час, статус, категорію помилки без паролів, секретних ключів або plaintext.

CLI перевірено реальним end-to-end сценарієм AES-GCM, AES-CBC+HMAC, RSA encrypt/decrypt, RSA-PSS sign/verify, гібридного encrypt/decrypt та ротації ключа; виконано перевірку `cmp` вихідних і дешифрованих файлів.

## 8. Ризики та обмеження

Це навчальний прототип: ключі присутні в оперативній пам'яті Python без гарантії zeroization, немає HSM/KMS, вхідні файли обмежено 64 MiB. У реальній системі необхідні захищений процес управління секретами, контроль доступу, централізований журнал подій, перевірка залежностей і періодичне оновлення криптографічної політики.

Вимірювання на іншому обладнанні можуть бути іншими. Тести підтверджують задані сценарії, але **не** становлять незалежного аудиту або криптографічної сертифікації.
